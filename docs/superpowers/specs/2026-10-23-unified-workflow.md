# 统一交付控制层

目标：开场、清理、设备、Google、VPS、服务端、电脑网络、AdsPower、手机代理、时区定位、手机验收、支付准备、App、登录、订阅均由一份阶段定义推进。客户已有选择与实际完成结果复用，订阅订单及权益确认后结束。

入口为 scripts/workflow.py。next 返回当前阶段、所需字段、章节和阶段票据；submit 仅接受当前票据和结构化观察，由程序判定完成；run 仅执行当前阶段允许的内置命令并保存回执。所有变更使用同一锁和原子写入。状态保存在 .local/workflow/state.json，派生进度保存在同目录 progress.md，原 progress.md 保留为历史资料。

依赖变化按范围失效设备设置和检测。网络配置／generation 变化在下次调用时自动检查；账号、首次使用时间和已付款记录保留。旧进度按可复用的具体观察逐阶段迁移，笼统完成标记不会自动转换成当前事实。新 Apple ID 的默认等待由实际首次使用时间计算。

现有 network、Karing 下载和清理入口接入执行许可；登录前检查在已有统一状态时回到统一入口。详细教程负责解释当前动作，阶段顺序和完成状态以控制层为准。

控制范围是本项目入口和已接入脚本。独立 Codex 的原生浏览器／手机工具由宿主提供，本项目无法拦截其任意调用；页面工具由当前阶段的动作约定与观察提交接入。来源记录用于追溯，不能被描述为独立证明任意 UI 操作已发生。

验证：全阶段完成、提前提交、伪造通用 passed 标记、过期票据、重复提交、逐项遗漏、进度恢复、执行中断、节点与时区变化、付款记录保留、Apple 等待、Windows／Android 分支、内置脚本直调、无统一状态的旧入口兼容。

## 对抗性审查后的修正

每个阶段维护检查批次，失效时更新批次，脚本回执必须同时匹配阶段批次和网络配置代次。更换电脑、重置网络后重新取得回执；历史保留供追溯。

阶段内更换 AdsPower 环境或 Apple 账号时，从新对象的观察开始。Apple 账号以本机代号保存类型和养号起点；更换手机重新核对商店登录及支付条件，同一账号复用养号起点，另一账号独立计算。账号类型纠正后使用新类型的字段集合。

Windows 恢复目录先在目标磁盘暂存、校验，再原子移回，恢复进度写回批次。服务端部署续跑按实际 systemd 状态启动已停止的托管服务，再读回验收。

回归覆盖：旧探针及服务端回执失效、部分提交中更换环境、同账号换手机与换账号等待、双向纠正账号类型、恢复中断与内容校验、恢复期间出现新数据、发布恢复结果后中断、已停／运行中服务的续跑。用户于本轮授权修复并整体发布。
