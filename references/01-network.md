## VPS 和家宽怎么理解

进入 VPS 阶段时先解释：VPS 就是您租用的一台远程服务器，我们把它配置成自己的魔法节点。您在网站完成购买，Codex 接着部署，再把电脑和手机连接到这条线路。

客户问到家宽时再展开：在 VPS 搭配家宽的路线里，VPS 负责运行节点和转发流量，家宽负责最后的网络出口。连接顺序是“电脑／手机 → VPS → 家宽出口 → Claude”。配好后，三个网站检测的是最终的家宽出口，电脑和手机也按这个目标出口核对。先了解客户现有家宽产品的接入方式，再沿当前阶段安排；默认路线继续使用已选 VPS。

## 配置期间先保住 Codex 的网络

**默认顺序：保留旧 VPN → 配置新节点 → 单独测试新节点 → 安排切换 → 复验新线路与 Codex。**本篇“关闭系统代理、开启 TUN＋全局”是新线路接管后的目标状态，不是在部署开始时先切断原有网络。

1. **先确认当前连接。**记录 Codex 目前依赖的 VPN 客户端、节点与接管方式，以及怎样重新连接。部署服务器、导入节点期间保持旧 VPN 可用，不提前退出旧客户端、停掉旧内核或清除 Codex 正在使用的系统代理／环境代理。不要把仍在使用的配置当作“残留”删除。
2. **保留旧 VPN，单独验证新节点。**新客户端优先只启动本机 HTTP 测试入口（可使用混合端口的 HTTP 能力；只有 HTTP 确认不可用／不兼容且 SOCKS5 实测可用时才用备选并记录原因），暂不开新的 TUN 或系统代理，不让两个客户端同时争抢全机路由。让测试请求明确经过新客户端的实际监听端口与目标节点，结合请求日志核对出口为目标 VPS 的实际出口；不能拿普通浏览器仍经旧 VPN 打开网页、端口可连接或延迟数字当作新节点成功。客户端不支持这种测试方式时，按下方例外流程处理。
3. **测通后再切换。**先把恢复办法告诉用户，安排关闭旧 VPN 的接管、开启新客户端 TUN＋全局并关闭系统代理。保留新客户端供 AdsPower 使用的本机 HTTP 入口。根据实际客户端安排动作，避免两个 TUN 长时间同时接管。旧 VPN 尚在运行时的新节点测试只证明当时的连通性，可能仍借用了旧 VPN 的传输路径；切换后必须重新验证，不能直接当成独立线路已通过。
4. **切换后确认能继续。**确认旧 VPN 不再接管、新节点实际出口正确，再请用户在 Codex 发一句“继续”，确认能收到新的回复。两项都通过才继续后面的浏览器配置；只看到 VPN 图标或检测网页能打开不算 Codex 已恢复。切换失败时先恢复旧 VPN，不在失联状态继续盲改。

### 后台测通，切换后 Codex 却掉线

**以下任一情况出现就主动进入排查，不等客户说“库里有案例”：**新节点后台测试通过，但旧 VPN 断开后 Codex 持续重连、收不到新回复；相同设置反复切换失败；或用户明确反馈新节点无法使用。没有抓到报错，也要先标记“切换失败／待验证”，不能沿用后台测通的结果写“连接成功”。

1. **切换前先留下恢复与续查安排。**把具体手动恢复方法显示给用户，已有安排直接复用；在本机进度中先写“切换待验证”，保存原接管方式、客户端／内核版本和网络栈，下一步写“若切换失败，先恢复旧 VPN，再执行第十节下一项修复”。
2. **掉线先恢复旧连接。**用户按预先给出的步骤恢复旧 VPN；Codex 恢复后立即读取切换记录并继续修复，最终在新线路下单独验收。
3. **恢复后直接执行修复。**按第十节读取当前配置、保存原值，并执行适用的下一步：TUN mixed 改 gvisor → 校正节点参数、服务和时间 → 应用已验证的 REALITY 版本／目标配置组合。环境读取与修改由 AI 完成，日志随复测一起记录；已经尝试无效的步骤直接跳过。
4. **按结果继续。**每完成一项就复测，成功即保留，无效则恢复并进入下一项。Windows v2rayN 按对应客户端的参数、服务与路由修复。已有方案均已尝试后，依据本轮失败请求继续定位。
5. **重新完成真正的交接验收。**在旧 VPN 已不承载流量、新客户端 TUN＋全局接管的状态，发起新的 HTTPS 请求核对目标 VPS 出口，再由用户向 Codex 发新消息确认收到新回复，并实际重试原先失败的操作。检查 Codex 是否仍依赖旧代理或环境配置。缺任一项记“待验收”；不能用既有连接、缓存页面、延迟数字或恢复旧 VPN 后的回复替代。

**旧 VPN 冲突的处理：**AI 检查实际路由和 TUN 接管。需要断开旧 VPN 进行测试时，先给出下面的恢复动作，替换成实际软件、节点及按钮名称，随后执行切换测试：

> 接下来需要暂时断开旧 VPN，测试新线路。如果断网，或 Codex 一直无法回复，请您先关闭新客户端的连接／TUN，再打开原来的 VPN、选择原来的节点并重新连接。恢复网络后，在 Codex 发一句“继续”，我们再排查。

恢复动作写明旧客户端、节点和按钮；原来依靠系统代理联网的，写明恢复模式。已有安排直接复用，用户找不到入口时再协助定位。

**后续断线测试使用同一套恢复安排。**AI 先读取当前联网依赖，准备并展示恢复动作，再测试节点不可达、客户端退出或路由变化。测试使用无登录页面；恢复连接后继续修复与验收。

## 一、基础概念（大白话版）

### （一）先搞懂上网是怎么回事

你打开浏览器输入 `youtube.com`，为什么就能看到视频？

你的电脑  ──发送请求──>  youtube服务器  ──返回数据──>  你的电脑

![](../assets/images/network/02.jpg)

简单说：你的电脑是个"寄信人"， youtube 是个"收信人"，你们之间一来一回，就上网了。

### （二）IP 是什么

IP = 身份证号。每台联网的电脑都有一个独一无二的身份证号（例：`203.0.113.10`），用来标识"我是谁"。

网站也有身份证号。你访问 `youtube.com` 时，浏览器会先查"youtube的身份证号是多少"，然后才能发请求。

### （三）IPv4 / IPv6 是什么

| 类型 | 身份证号长这样 | 现状 |
| --- | --- | --- |
| IPv4 | `203.0.113.10` | 大多数网站都用它 |
| IPv6 | `2001:0db8:...` | 新版，号码更多，但有的网络不支持 |

不用纠结：教程全程用 IPv4，用不到 IPv6。

### （四）VPS 是什么（重点！）

VPS = 在云端租一台永远开机的电脑

你本地电脑关机，VPS 还在跑

VPS 可以在任何地方登录（公司、网吧、手机都行）

这台电脑归你全权控制，想装什么软件都行

通俗理解：相当于在云端养了一台 24 小时待命的"服务器"，专门帮你处理网络请求。

### （五）静态 IP 是什么

静态 IP = 固定不变的身份证号

动态 IP = 每次上网随机分配的身份证号

为什么要静态 IP？

你需要从公司/家里登录 VPS 管理它

如果 IP 天天变，你还怎么登录？

很多网站会检测 IP 稳定性，静态 IP 更不容易被封

### （六）机场是什么

|  | 机场 | 自建 VPS |
| --- | --- | --- |
| 谁提供的 | 商家搭建，你花钱买 | 自己搭建 |
| 节点数量 | 一堆国家可选 | 只有 1 个（你买的 VPS 所在地） |
| IP 状态 | 很多人共用，IP 容易"变脏" | 专属 IP，只有你一个人用 |
| 速度 | 高峰期可能卡 | 取决于你买的 VPS 线路 |
| 价格 | 每月 10-100 元 | VPS 每月约 10-100 元 |
| 稳定性 | 商家跑路就凉凉 | 只要 VPS 不跑路就没事 |

通俗理解：

机场 = 坐公交，人多挤、司机（商家）可能心情不好（不稳定）

自建 VPS = 自己开车，想怎么开怎么开（很稳定）

### （七）本文到底搭建的是什么东西（是不是 VPN）

官方叫法：VLESS + REALITY 协议（一种加密通信方式）

通俗叫法：自己搭的"科学上网通道"

是不是 VPN：

传统 VPN（如公司用的）确实是这个原理

但技术上不完全一样（协议不同）

效果一样：开着软件 → 走 VPS 通道 → 访问海外网站

效果一样：关掉软件 → 走本地网络 → 访问国内网站

### （八）机房 IP / 住宅 IP

| 类型 | 怎么来的 | 特点 | 适合谁 |
| --- | --- | --- | --- |
| 机房 IP | 云厂商数据中心分配 | 速度快、带宽大、价格便宜 | 大多数人（教程用的） |
| 住宅 IP | 家庭宽带分配 | 看起来像"真人"，不容易被封 | 需要高隐匿名性的人 |

>教程用机房 IP，普通人足够用，性价比最高。

### （四）打通网络与防火墙（最容易卡关的地方）

如果安装器输出的 Access URL 打不开，先检查服务器防火墙是否放行了面板端口（下面以 8899 为例）。后面创建节点时，节点端口也需要按实际配置检查放行。

在终端输入 x-ui 回车调出菜单，选择 22. Firewall Management（防火墙管理）。

💣 【新手踩坑记录 3：找不到 ufw 命令】症状：在防火墙菜单里选择放行端口，系统却报错 /usr/bin/x-ui: line 829: ufw: command not found。

真相：Debian 纯净版系统默认没有安装 ufw 防火墙管理软件。

避坑指南：在防火墙菜单下，先输入 1 (Install Firewall) 并回车，系统会自动帮你安装好。安装完后，再输入 3 (Open Ports)，然后输入你的端口号（如 8899），看到 Rule added 就说明放行成功了。

💣 【新手踩坑记录 4：浏览器打不开，以为被 GFW 墙了】症状：防火墙放行了，但浏览器依然转圈打不开。

真相排查：不要盲目猜疑！打开测试网站 👉 https://ping.pe，输入 IP:端口 测试。如果下面表格里全球（包括 China）都是绿色的 successful，说明服务器网络完美畅通！

如果 ping.pe 显示端口可达，但本机浏览器仍打不开，继续检查本机代理设置、实际访问的协议和完整路径。优先使用安装器输出的 Access URL：输出为 https:// 时保留 HTTPS，不要套用 HTTP 示例。

### （七）底部状态栏全解

v2rayN 软件最下方的那一排状态栏，是决定你电脑怎么上网的核心区域。从左到右分为四个模块：

模块一：本地端口信息区

本地: [mixed:10808]

局域网: none

本地：10808 只是这张旧图的示例，实际端口读取当前配置和监听结果。它是 v2rayN 在你电脑上开的"内部收发室"。你电脑里的浏览器、软件想翻墙，都会把数据先送到这个门牌号里。

这里的 `mixed` 表示 HTTP／SOCKS 混合代理入口，与 Karing「TUN → 网络栈」中的 `mixed` 不是同一个设置；排查时不要改错位置。两种代理均可用时，新节点测试与 AdsPower 都优先 HTTP，保留实际混合端口即可，不必关闭 SOCKS5 或修改 TUN 网络栈。HTTP 入口先实际请求验收，不只是改浏览器下拉框。

局域网：none 表示没有提供对应局域网入口，不代表其他设备是否具备网络能力。AdsPower 只需本机入口，不为此开启局域网共享；手机导入服务器节点后独立配置。

模块二：启用 TUN

本教程保持开启。查看实际虚拟接口、路由和新请求，确认流量被接管，不只看开关颜色。

模块三：系统代理

选择清除／关闭系统代理，保留客户端与本机 HTTP／混合入口运行。不开系统代理也可以通过 TUN 接管网络。

模块四：路由

选择全局（Global），固定走本次 VPS 节点，不默认选择绕过大陆或自动切换节点。全局会增加 VPS 流量使用，这是本教程为简化路径采用的默认选择。

最终逐项记录：TUN 已开启、系统代理已关闭、全局已开启、当前节点正确、实际出口符合预期、断线行为已检查。旧截图只用于定位区域，开关值按上述文字和当前界面核对。

## 九、容易踩的坑——排雷必看！！！

### （一）两个代理抢控制权

多个客户端可能争抢系统代理或 TUN 路由，也可能留下后台内核。系统代理被旧软件改变，不等于新的 TUN 必然失效；按本轮路由、监听、进程与实际请求判断冲突。本教程最终使用 TUN＋全局、系统代理关闭。

处理：先按本篇“配置期间先保住 Codex 的网络”确认当前联网依赖和冲突依据。默认保留旧 VPN 单独测试新节点；必须退出旧客户端才能排查时，先给出具体手动恢复步骤，随后执行测试。切换后核对 TUN 开启、系统代理关闭、全局代理开启、实际出口与 Codex 新回复；失败先恢复旧连接。

### （二）-1ms / none 的常见原因

原因 说明     服务端端口没通 防火墙/安全组/iptables   REALITY 握手失败 时间偏差   客户端权限或网络组件异常 TUN 未正常接管   公钥私钥未生成 我真实踩的坑

### （三）在 Windows PowerShell 里敲 iptables

错误原因：iptables 是 Linux 命令，只能在 SSH 登录后的 VPS 里敲。

你踩到的表现：PowerShell 报 && 分隔符无效、iptables 不认识。

正确做法：先 ssh root@IP 进入 root@vps:~# 再执行。

### （四）Let's Encrypt 证书申请失败

常见原因：80 端口不通/被占用。

处理要点：确保 VPS 外网能访问 80；安装时选默认 80。

### （五）"关掉 v2rayN 就没网"

先区分显式使用本机代理的应用失去入口、残留系统代理／路由、明确配置的阻断策略，不能一概当成正常。TUN 退出也可能恢复直连，并不天然保证所有应用断网。按 Windows 专章先准备恢复办法，再分别验证节点失效与客户端退出；不通过全机网络重置试错。日常使用时保持客户端运行，明确区分最小化与退出。



## 十、Karing REALITY 握手失败

新交付已在安装阶段配置好本节的固定版本组合。本节处理已有设备或交付过程中出现的连接故障；AI 读取当前版本与参数，已匹配的项目直接进入下一项检测。

**触发即执行：**用户反馈 Karing 连不上、出现 `reality verification failed`、切换后 Codex 断连，或新节点反复连接失败，就进入本节。AI 自行读取环境、保存原值、修复并复测；用户已经要求配置或修复时，沿用这份授权连续完成。

给用户的开场话术：“我先按已有方案修复 Karing，完成后检查实际连接。”随后直接操作。日志用于判断每步效果和选择下一步；“是否属于已知兼容问题”由 AI 在执行中判断。需要用户配合时，只提出缺失的访问方式、本人验证或当前工具无法完成的具体动作。

**执行顺序：可用网络与原配置 → 适用时试 gvisor → 自动校正参数、服务与时间 → 应用已验证的 REALITY 组合 → 重新导入并验收。**任一步成功就继续交付；进度中已有的无效尝试直接跳过。

### 1. TUN 场景先试 mixed 改为 gvisor

AI 打开 Mac Karing「设置 → TUN → 网络栈」，读取当前值。TUN 正在使用 `mixed` 时，记录原值并改为 `gvisor`，保存、重连，随后验证实际 HTTPS 请求与出口。操作期间按本篇网络交接流程保留 Codex 的可用连接，并提前给出具体恢复动作。

修复有效就保留，进入第 4 小节验收。无效则恢复原值，继续第 2 小节。已经使用 `gvisor`、没有此选项，或错误发生在未启用 TUN 的本机 HTTP 入口测试中，直接执行第 2 小节。

### 2. 自动校正基础配置

以下步骤由 AI 自行完成，发现具体错误就修正并复测：

1. 备份服务端入站配置、Xray 程序和版本、Karing 节点配置，记录原值与恢复方法。
2. 从面板导出或读取实际节点参数，校正客户端地址、端口、UUID、Flow、传输、SNI、公钥和 Short ID。链接和密钥保存在本机。
3. 检查并恢复 VPS 服务、节点监听及预期端口放行，校正两端时间。读取本次请求对应的日志。
4. 检查本机实际 HTTP 入口和当前代理接管，修正冲突设置。保持可用旧线路，通过 Karing 的指定入口测试新节点；需要线路交接时使用已经准备好的恢复动作。

基础配置修正后仍失败，就执行第 3 小节。独立 Xray 客户端可作为进一步诊断工具，已有修复流程可以直接推进。

### 3. 执行已有 REALITY 修复组合

保留 Karing，使用以下已有成功配置修复故障节点：

| 配置项 | 修复配置 |
| --- | --- |
| VPS 上的 Xray | 26.7.28 |
| REALITY minClientVer | 1.0.0 |
| REALITY 目标（target / dest） | www.cloudflare.com:443 |
| 服务端允许的 SNI 与 Karing SNI | www.cloudflare.com |

AI 使用当前面板的 Xray 内核版本管理，或官方对应架构的发行包，将服务端 Xray 切换为 `26.7.28`；读取实际运行版本。随后同步目标、允许的 SNI 和客户端 SNI，保留本节点的地址、端口、UUID、公私钥及 Short ID，重新导出、导入并重连。将这组互相配合的参数作为一次完整修复尝试，保存修改前后的配置与测试结果。

Xray 内核由服务端入站共用，切换后同时检查服务状态及其余入站。修复有效就保留；无效则恢复这组原配置，读取本轮客户端与服务端日志，继续定位下一项。


**脚本创建的节点同步记录：**完成修复后，AI 按实际服务端配置同步本机 `.local/network/input.json` 的 `server.sni` 和服务器 `/var/lib/claude-setup-network/receipt.json` 的 `config.sni`，保留已有节点身份字段与面板版本。使用脚本的原子保存方式写入，随后执行 `python3 scripts/network.py invalidate`、`python3 scripts/workflow.py run --action server_export`，再检测实际连接。这样后续导出和续跑会沿用修复后的目标。恢复原配置时同步恢复这两处记录。已有其他面板按其原导出流程处理。

### 4. 修复后直接验收并继续

- 通过 Karing 实际 HTTP 节点入口访问 `https://www.google.com/generate_204`，取得 HTTP 204，并核对出口为当前 VPS。
- 验证 AdsPower 将使用的实际代理入口；节点入口与规则入口分别按实际配置检查。
- 完成网络交接后，在旧 VPN 已不承载测试流量时验证新 HTTPS 请求、目标出口、Codex 新回复及用户原先失败的操作。
- 验收通过就记录保留的设置，继续浏览器与账号配置。已有方案均未解决时，汇报已执行的修复、各步结果和当前具体故障，再安排对应的进一步处理。
