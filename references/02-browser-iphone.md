## 1. 电脑端：AdsPower 配合本机代理

### Claude 桌面版、Claude Code 和 AdsPower 分别做什么

**这套流程完成后，您可以用 Claude 桌面版，也可以用 Claude Code。**先分清这三个工具：

- **Claude 桌面版**：就是下载安装到电脑上的 Claude 软件，打开软件就能和 Claude 对话。
- **Claude Code（CLI）**：这里说的是在电脑“终端”里使用的 Claude 编程工具，主要用来帮您写代码、改项目。
- **AdsPower 指纹浏览器**：就是我们现在要配置的浏览器，给 Claude 准备一个独立登录环境。

**AdsPower 什么时候用？**按本教程，电脑浏览器中所有需要登录 Claude 账号的场景，都在这个已配置好的 AdsPower 环境里完成。比如网页登录、邮件里的登录链接，或 Claude 桌面版、Claude Code 弹出的浏览器授权链接，都放到这里打开。登录或授权完成后，回到原来的 Claude 软件或终端继续使用。

**关于 Claude 桌面版，您需要知道这两点：**
- 有人担心，Claude 桌面版可能要求更多电脑权限、读取更多设备信息，从而增加账号被封的风险。
- 我们已经交付的用户中，也有不少人反馈：一直在用 Claude 桌面版，目前使用正常。

这两方面都告诉您，具体用 Claude 桌面版还是 Claude Code，按您的使用需要和接受程度来选。

手机首次登录与订阅继续按后面的手机流程完成。

Codex 在首次介绍指纹浏览器时主动展示以上用途与选择说明；客户再次问“是不是只能在指纹浏览器里用”时，直接说明桌面端与 CLI 的使用方式，并保留传闻和已交付用户反馈各自的来源。

本章 Mac 示例使用 Karing；Windows 使用 [Windows 专章](10-windows.md)中的 v2rayN，以下 Karing 的 HTTP 入口与节点检查对应换成 v2rayN 实际入口。Windows 环境选择 Windows，不照抄 Mac 的界面和参数。

前一篇已经把 DMIT 的 VLESS + Reality 节点导入 Karing。这一篇继续使用这条线路，在 AdsPower Global 里新建独立浏览器环境，把浏览器连接到这台 Mac 上的 Karing。

**连接顺序：AdsPower → 本机 HTTP 代理入口 → Karing → DMIT VPS → 网站。**

VLESS + Reality 是 Karing 连接服务器时使用的节点协议；HTTP 是 AdsPower 连接本机 Karing 时使用的代理类型。

**本机代理类型优先 HTTP。**HTTP 与 SOCKS5 都支持时，AdsPower 选 HTTP，包括同一个 `mixed` 混合端口；混合端口无需改成仅 HTTP，也不需要关闭 SOCKS5 监听。先用 HTTP 入口发起 HTTPS 请求并核对出口。HTTP 失败先查地址、端口、认证和节点，只有确认 HTTP 不可用／不兼容而 SOCKS5 实测可用时才作为备选，记录原因及 DNS、出口验收；不要来回切换碰运气。已有 SOCKS5 环境正常时保留，用户希望调整再备份后验证。

这只决定浏览器连接本机客户端使用什么代理类型，不改变客户端到 VPS 的 VLESS＋REALITY 协议、TUN＋全局规则；也与 TUN 网络栈 `mixed/gvisor` 无关。不将 HTTP 优先解释成必然更安全或保证不封号。

### 1.1 先确认本机 HTTP 代理入口

Mac 的 Karing 连接报错时，先回到[网络章节的 Karing 修复流程](01-network.md#十karing-reality-握手失败)，继续使用 Karing 排查、按案例修复；即使其他客户端测通，也不因此首推换客户端。修好后再配置浏览器。

进入本章前应已按[网络教程](01-network.md)完成新旧 VPN 交接并确认 Codex 能继续回复；尚未完成时先回到该流程，不直接关闭仍在供 Codex 联网的旧代理。用户反馈切换后掉线或反复连不上，即使此前后台测通，也先恢复可用旧线路，直接执行网络章节第十节的修复步骤，测通后返回本章。

先打开 Karing，逐项确认系统代理关闭、TUN／Tunnel 开启、路由为全局代理，并确认上一章导入的目标 VPS 节点能够连接。本机 HTTP 入口继续保留，关闭系统代理不等于关闭这个入口。查看 Karing 当前的 HTTP 或混合代理监听地址、端口；如果自己找不到，把下面这段交给 Codex 检查。

请先只读检查这台 Mac 的 Karing 配置、系统代理和本机监听端口，找出确实支持 HTTP 的本机代理入口。分别核对监听地址、端口、是否需要认证，并通过该入口发起 HTTPS 请求，确认出口是我的目标 VPS。不要猜端口，不要把 VLESS 服务端端口或 SSH 端口当成本机 HTTP 端口。如果当前没有可用入口，先说明需要的改动并保留配置备份，再协助配置。不要覆盖我已有的浏览器环境，也不要公开输出节点密钥、账号密码或完整公网 IP。

请记录检查得到的**本机代理地址和实际端口**，供下一节填写。截图中的地址、端口已遮挡为说明文字，不能直接复制使用。本机入口指当前这台电脑上的代理服务；网页最终看到的是请求经过代理规则后使用的公网出口，所以还要核对目标网站的实际出口。

### 1.2 新建 AdsPower 环境并填写 HTTP

打开 AdsPower Global，点击左上角「新建环境」。新建一个专门的环境，保留原来日常使用的环境。

① 名称可以填「Claude 登录授权」；② 浏览器选择 SunBrowser；③ Mac 用户选择 macOS，Windows 用户选择 Windows。让 Codex 按你自己的电脑配置，浏览器内核选 AdsPower 当前支持的稳定版本，硬件参数尽量与本机一致。

![](../assets/images/browser-iphone/01.png)

切换到「代理信息」，代理方式选「自定义」，按下面的字段填写。

![](../assets/images/browser-iphone/02.png)

| 位置 | 填写内容 |
| --- | --- |
| ① 代理类型 | 优先 HTTP；混合端口同时支持 HTTP／SOCKS5 时也选 HTTP，备选条件见第 1.1 节前的说明。 |
| ② 主机与端口 | 主机填你自己检查得到的本机代理地址；端口填实际可用的 HTTP / 混合代理端口。图中已遮挡具体数值，不是可直接填写的参数。 |
| ③ 代理账号、密码 | 本例的本机入口没有认证，因此留空。如果你自己开启了入口认证，则填写该入口的凭据。不要填 DMIT 登录密码、SSH root 密码或 VLESS UUID。 |
| 刷新 URL | 本例留空。 |
| ④ 检查代理 | 点击后应显示连接成功，并检查返回的出口地区。失败时先检查 Karing 是否运行、端口是否正确、节点是否可用；不要靠切换 SOCKS5 碰运气。 |

### 1.3 时区、语言与浏览器设置

切换到「指纹配置」。下面是本例的实际设置，各项数字与图中对应。

![](../assets/images/browser-iphone/03.png)

1. WebRTC 选「禁用」。这样可减少通过实时音视频接口暴露其他网络地址的机会，但部分音视频功能会受影响。
2. 时区先按节点城市配置，本例为洛杉矶；手机阶段按第 2.3 节确认“跟随节点／台北”的选择后，电脑、手机和 AdsPower 统一采用所选时区。应使用城市时区，让夏令时自动处理，不要固定照抄 GMT 偏移量。
3. 地理位置选「禁止」，避免网站取得精确定位。
4. 浏览器语言本例选「自定义」的「英语（美国）」和「英语」；可以按用户需要保留中文，不把英文作为通过条件。语言与时区分开设置。
5. 界面语言可选「基于语言」或用户熟悉的中文，以当前软件支持为准。

**正常用简体中文和 Claude 交流就可以。**系统语言方面，按作者的配置建议，能适应英文界面的话，可以把电脑和手机一起改成英文；要改就两台一起改。提前告诉用户：改完后系统菜单和部分提示会变成英文，日常使用可能没那么方便。觉得不方便可以保留中文，英文不作为通过条件。时区按第 2.3 节所选的节点城市或台北设置，与使用什么语言分开判断。

继续向下检查硬件相关设置。本例将 Canvas、WebGL 图像、AudioContext、媒体设备、ClientRects、SpeechVoices 的噪音关闭，WebGL 元数据、WebGPU、CPU 和内存使用真实值。其余选项按实际设备与软件能力核对，不需要一键随机所有参数，也不要每次启动都生成新指纹。这些选项并不意味着浏览器所有特征都与本机完全一致。

点击「确定」保存，然后在环境列表中点击新环境的「打开」。后续电脑上处理 Claude 网页登录、相关邮件和授权链接，都在这个环境里完成；首次登录按下文先配置手机，再在手机 Claude App 用 Google 登录。

### 1.4 配好后先检查，再进入手机

「代理检查成功」只说明入口能连接。打开新环境后，还要在这个窗口里检查实际网络路径；不能拿其他浏览器的检测结果代替。

| 检查项 | 完成标准 |
| --- | --- |
| 实际出口 | 在新环境打开 [Ping0](https://ping0.cc/) 或 ipinfo.io，刷新后确认出口属于预期线路，并按下面的方式留存节点检测凭证。若使用分流，继续检查 Claude 相关域名的路由规则与连接日志；单个检测网站不能代表全部网站。 |
| IPv4 / IPv6 | 分别检查两种地址族；不能出现绕过预期代理的公网出口。IPv6 不可用应记录为不可用，不要写成已经验证通过。 |
| DNS / WebRTC | 检查 DNS 查询路径是否符合客户端规则，以及 WebRTC 是否暴露预期代理之外的公网地址。DNS 服务商与 VPS 不同本身不等于泄露，需要结合配置判断。 |
| 时区 / 语言 | 检测页读到的时区、语言与当前保存的配置一致；换地区后重新核对。 |
| 故障时是否直连 | AI 按网络章节读取 Codex 联网依赖，准备并展示具体恢复动作后执行，已有安排直接复用。在没有登录或付款操作时，分别测试「节点不可达但代理客户端仍运行」和「代理客户端退出」。使用无登录检测页发起新的请求，预期应失败，不能改走其他公网出口；测试后恢复配置。只选择 HTTP 并不自动保证两种故障都能阻断。 |

**三个检测网站分别记录：**

| 网站 | 本教程建议参考值 |
| --- | --- |
| [NetCoffee](https://ip.net.coffee/claude/) | 分数约 80 或更高，越高越好 |
| [Ping0](https://ping0.cc/) | 风险值低于 30 可接受参考，优先低于 25，越低越好 |
| [Scamalytics](https://scamalytics.com/ip) | 查询当前代理出口 IP，风险值最好低于 10，越低越好 |

电脑和手机分别检查，记录设备、时间和当前线路。三站数值分别保留，不直接平均；未取得结果写“未验证”。这些是本教程的选线参考值，配置检查仍须逐项完成。IPinfo 只作出口归属辅助查询，不列入这三个评分网站。

**留存 Ping0 节点检测凭证：**连接待测节点后，在这个 AdsPower 环境打开 https://ping0.cc/，记录检测时间、设备与浏览器环境、节点名称，以及页面显示的出口地区、ASN / 运营商、IP 类型、风控值、原生 IP 和共享人数。截图先隐藏完整 IP，保存到本机 `.local/`，在 `.local/progress.md` 记录结果及截图的相对路径，不提交到教程仓库。

Ping0 的风控值越低表示该站评估的风险越低，不套用 Claude 检测的“80 分以上”。这些标签和人数是第三方页面的评估，不单独证明住宅属性、独享节点或账号安全。遇到人机验证时由用户在页面完成；页面打不开或某项没有结果，记录“未验证”，不能引用示例截图的数值。

可以把下面这段连同本文交给 Codex：

请检查我刚新建的 AdsPower 环境，不要修改现有环境。确认它使用本机实际可用的 HTTP 入口，经 Karing 的目标节点访问网页。在该环境内检查出口 IPv4 / IPv6、DNS、WebRTC、时区、语言及目标域名的分流规则。把每项结果写成「通过 / 未通过 / 未验证」，并给出依据。断线测试会影响联网，先确认当前没有进行登录或付款；如会中断 Codex，按网络章节提前说明如何关闭新连接并恢复旧 VPN，确认我知道如何恢复后再测，再分别测试节点不可达和 Karing 退出，记录是否出现直连并恢复配置。只输出脱敏结果；遇到验证码、密码或身份验证，让我本人完成。

同时在该环境打开 Ping0，按本节要求记录节点检测结果和脱敏截图，作为本次检测凭证。各项以实际页面为准，未取得的结果标为“未验证”。

### 1.5 浏览器配置完成后，直接进入手机

电脑检查通过后，直接进入第 2 节配置 iPhone 网络，不主动带用户在电脑网页注册 Claude，也不默认注册 Proton 邮箱。Google 账号按[账号准备与两步验证](08-google-account.md)在前面确认；首次 Claude 登录默认在手机官方 App 中使用 Google 完成。只有用户明确要求电脑注册时才按其要求处理。

此时主动解释：**AdsPower 是给 Claude 准备的独立登录环境，把相关登录记录和浏览器设置与日常上网分开。**网页登录、相关邮件链接和授权链接在这个环境中处理，完成后回到电脑的 Claude 桌面端或 CLI 使用。手机主要用于首次登录和订阅。

### 1.6 登录前的提醒与交付顺序

手机网络检查完成、首次登录前再简短提醒：

> 手机主要用于这次登录和订阅，后续在电脑的 Claude 桌面端或 CLI 使用。相关邮件链接、网页登录和授权链接放在已配置的 AdsPower 环境里处理，完成后回到桌面端或 CLI。

邮件跟踪内容可能在加载时产生网络请求，不是向电脑安装程序。不要把“开过邮件”直接认定为封号原因。

接下来按顺序做：手机网络配置 → 电脑与手机时区、定位设置 → 手机网络验收 → 核对美区 Apple 账户、养号记录及余额／礼品卡 → 保持节点开启，下载官方 Claude App → 手机 Google 登录 Claude → 手机 Apple 内购 Pro → 核对订单与权益，结束交付。操作细节见[带做指南](05-ai-walkthrough.md)和[Apple 章节](03-apple.md)。Google 登录需要两步验证时，读取[字段说明与操作步骤](08-google-account.md)。

日后用户自行使用 Claude Code 时，提醒其把默认浏览器弹出的完整授权链接复制到已配置的指纹浏览器，再完成网页授权。Claude Code 的安装和使用教学不属于本次交付；保留文末的网络排查资料，仅在用户明确需要时读取。

安卓用户在网络验收后走[安卓官网 Google Pay 分支](11-android-web-pay.md)：手机浏览器用于此次登录与付款；以下 iPhone 镜像、App 登录和 Apple 订阅要求不套到安卓。电脑日常使用 Claude 桌面端或 CLI，网页登录与授权使用已配置的指纹浏览器。

## 2. 手机端：Codex 配合 iPhone 镜像配置网络

**电脑网络和 AdsPower 验收后，必须继续完成手机代理、时区与定位、手机网络验收，再衔接手机登录和订阅。**按实际设备进入 iPhone／iPad 或安卓分支，手机网络使用独立检测结果。日常主要使用电脑也按这条主流程完成交付。

### 2.1 按电脑平台选择手机带做方式

**Windows＋iPhone：**默认使用本章对应图解逐步操作，并收集手机截图／口述核对；有实际可用的手机操作工具才代做。Windows 不支持 Apple 原生 iPhone 镜像，不要求完成下面的 Mac 镜像排查。Android 用户转网络教程的 Android 配置，手机网络自检通过后读取[安卓官网 Google Pay 基础指引](11-android-web-pay.md)，先提示风险再继续，不套用 Apple 内购。

**Windows＋iPhone 的每轮带做格式：**先说「现在只操作 iPhone」或「现在在 Windows 电脑上操作」，每轮给 1～3 个相连动作，再说明应出现的页面或结果。电脑负责展示现有节点二维码、保存本机资料和核对结果；手机负责小火箭、Safari、微信和 App Store 的实际操作。客户说「打不开／IP 还是北京／发不了图片」时，先确认设备、App／网址和当前 Wi-Fi／蜂窝网络，再进入对应排查。

- **导入节点：**Codex 在 Windows 打开已有节点二维码，客户在 iPhone 小火箭首页使用扫描入口导入；依据当前页面定位按钮。导入后核对新增条目的名称并选中，看到首页选中标记后再开启连接。先用「首页里刚导入的那一行」描述，再解释这就是节点，避免只说「开启自建节点」。
- **页面反馈：**每轮只索取当前操作需要的页面；找不到入口时看当前截图再定位。客户说「好了」后核对本轮可见结果。节点凭据与完整配置保存在客户本机，聊天仅发当前所需的脱敏局部截图。
- **出口核对：**在 iPhone Safari 打开检测链接，读实际显示的出口并与目标 VPS 在本机对照；记录检测网站、网络类型和结果。微信等已设直连的应用、手动输入 IP 的信誉查询，以及网页的城市标签分别记录用途。
- **修改与恢复：**按第 2.2.4 节准备恢复记录；需要修改 DNS 时按第 2.2.5 节逐步添加、回读和复测。每次变更只处理一个项目，确认结果后再继续。

**以下镜像优先与排查步骤仅适用于 Mac＋iPhone。**

iPhone 镜像是新手导入节点和配置网络的关键辅助方式。默认优先用 **Codex Computer Use + iPhone 镜像**读取手机界面、导入节点、选择路由并核对结果；不要只发一份教程就让用户自己配。镜像没有开启或连接失败时，先帮助用户把它配置好，逐项排查并重试，不直接退回手动配置。

1. 按当前 Apple 官方说明和设备读取结果核对 Mac、iPhone 的硬件与系统要求，先尝试镜像连接。若实际出现地区不可用报错，再按该报错处理；普通配置直接沿用节点出口和账户设置。Windows 按其手机操作路线继续。
2. 核对两台设备是否使用同一个 Apple 账户并启用双重认证，Wi-Fi 与蓝牙是否开启，设备是否靠近，iPhone 是否处于镜像要求的锁定状态；按当前界面的提示处理其他连接冲突。
3. 检查 Mac 上 iPhone 镜像的首次设置、连接授权，以及 Codex Computer Use 是否能读取和操作这个窗口。能够看到镜像不等于工具可以点击；用实际页面读取和一次普通导航确认操作能力。
4. 根据实际报错修复权限、连接或兼容问题，必要时重新连接、重开应用后重试。会中断当前网络或操作的步骤先说明影响，记录尝试和结果，不盲目反复重置设备。

密码、验证码、Face ID、系统授权和购买客户端的付款由用户完成；需要用户在实体手机上处理时，带他完成必要动作，再恢复镜像连接继续配置。节点通过用户本机的导出链接或现有二维码导入，不要求把完整 VLESS 链接、密钥发到聊天，也不把参数写入公开文档或进度文件。界面操作依据真实页面，不编造导入按钮或路径。

**只有确认设备／地区不支持，或有具体记录的排查仍无法让镜像与 Computer Use 可用时，才说明阻碍和已尝试的办法，改用其他可用的手机操作工具；仍不可用时才逐步指导用户手动操作。**用户明确要求手动操作时按其选择。镜像不可用不等于可以跳过手机网络配置和验收。

### 2.2 导入节点并设置小火箭全局路由

手机端使用支持 VLESS + Reality 的客户端（例如相应版本的 Shadowrocket），将上一章同一条服务器节点导入手机，再核对节点参数。**不要把电脑 AdsPower 的本机代理地址和端口照抄到手机：**本机回环地址在手机上指向手机自己。这里要复用的是服务器节点，不是电脑的本地 HTTP 入口。客户端尚未安装时先按当前官方购买／下载流程准备，不默认用户已经有小火箭。

使用 Shadowrocket（小火箭）时，选中导入的目标节点，**将「全局路由」设为「代理」，开启连接并确认系统 VPN 已连接**。这是本教程手机登录和订阅期间的默认配置，最接近电脑的「TUN 接管 + 全局代理」。先记录原配置；日常使用需要恢复其他模式时按用户选择，下一次使用 Claude 前重新检查。

| 全局路由模式 | 区别与本教程要求 |
| --- | --- |
| 配置 | 按配置中的规则分流，部分流量可能直连；不能直接当成全部流量走节点。 |
| 代理 | 将 VPN 接管且没有被排除的流量送到选定代理节点；本教程手机使用 Claude 期间选择此项。 |
| 直连 | 接管后的流量直接连接目标，不符合本教程此阶段的要求。 |
| 场景 | 按设置的网络场景自动切换策略；结果取决于场景配置，不能凭名称判断为全局代理。 |

TUN／VPN 是接管流量的机制，以上模式决定接管后的去向；电脑仅开启 TUN 也不代表所有流量走代理。**「代理」不等于已证明手机所有流量绝无绕行，也不保证 VPN 关闭后仍阻断网络。**继续按第 3.1 节检查排除路由、DNS、IPv6、实际出口、App 请求路径和断线行为，不凭模式名称或 VPN 图标判通过。其他手机客户端按实际功能核对等效设置，不照搬小火箭按钮名称。

默认选“代理”是为了让新手的路径简单、一致，不代表其他路由模式在技术上都不可用。用户明确保留其他模式时，检查该模式下目标流量是否仍走指定节点、是否有直连或泄露，逐项验收并记录；不能只凭模式名称判通过。

#### 2.2.1 小火箭全局超时：先试 Chrome 140

**先按实际受影响范围处理：检测页和其他网页正常、只有微信图片异常时，按第 2.2.3 节处理微信访问。小火箭开全局超时、节点连不上或手机网页打不开时，若刚做过断线测试、改端口或切换配置，先按第 2.2.2 节恢复并核对刚才改过的项目；其余全局超时反馈先给出本案例和下面的尝试步骤。**这是首个尝试方案，不先要求判断“是否适用”，不先索要客户端版本、完整日志或诊断包。尤其是 Windows＋iPhone 等需要手动配置的客户，先让他在手机上试；有实际可用的操作工具时可以协助，但不能把镜像可用等同于已经查明故障。

先在对话中直接告诉用户：

> 有用户反馈过“小火箭 TCP 测试有延迟，但 CONNECT 一直超时，商店也下载不了”。我们先试一个调整：打开小火箭当前节点的设置，找到 **TLS 指纹**，先记下原来的值，再改成 **Chrome 140**，保存后重新连接，全局路由仍选“代理”。然后再试 CONNECT 测试、手机网页和刚才失败的操作，告诉我有没有恢复。找不到这个选项，就把当前设置页截图发给我，遮住节点地址、账号和密钥；没有改善的话，我们恢复原值再查下一项。

此案例目前是客户反馈的症状与建议尝试方向，尚未取得原客户改完恢复的结果，不能说“已验证一定能修好”。这里调整的是小火箭的 TLS 指纹，不是 AdsPower 内核或 User-Agent；TCP／CONNECT 若为延迟测试选项，不要误改节点传输协议。

1. **先给方案，再按页面操作。**不要让客户先回答一串诊断问题。先记原值，只改 TLS 指纹，保存并重连；路由仍为「代理」，节点、DNS、服务端版本等不同时改。原配置留在本机，不发送节点链接或密钥。只有全局指纹入口时，说明会影响其他节点，由用户确认后再改。登录或支付中的操作先完成或暂停；手机给电脑提供热点时先交代恢复方法，保住 Codex 联网。
2. **找不到选项时再看截图。**按实际页面找 TLS 指纹及 `Chrome 140`；确认当前客户端没有该选项时就转其他排查，不猜按钮、不填未支持的值、不为此盲目降级。已经是该值或本次相同设置已试过无效，不重复修改，直接接下一项排查。此方案只用于客户反馈的小火箭故障，不主动改正常连接或其他客户端；只有 Apple 付款／账号报错时不套用网络故障案例。
3. **按原场景复测。**同一节点、网络和测试地址下复测 CONNECT，再用手机浏览器发起新的 HTTPS 请求并核对出口；商店原来下载失败的，再确认原操作是否恢复，不自动购买或重复付款。只有 TCP 延迟不算修复。CONNECT 超时但网页正常时单查测试地址；网页正常而商店异常时按商店报错查，不认定整个节点不可用。部分恢复逐项记录。
4. **有效保留，无效恢复。**原故障消失、实际请求和出口通过才保留，再补记客户端版本和环境，继续第 3.1 节手机验收。无改善、恶化或无法验收时恢复原值并核对结果，再查导入参数与服务端是否一致（地址、端口、UUID、Flow、SNI、公钥、Short ID）、客户端错误、服务端日志、DNS 与所用网络。每次只改一项，不循环试指纹，不直接套 Mac Karing 的 `mixed → gvisor`。

记录案例是否已给出、原值／试验值、前后结果与恢复状态。未取得实际反馈的项目保留「未验证」，不能把“已让用户改成 Chrome 140”记成配置成功。

#### 2.2.2 断线测试后恢复端口，手机仍无法联网

**客户反馈案例（已补齐后续对话）：**Windows＋iPhone，Shadowrocket 使用 VLESS＋REALITY、Flow 为 `xtls-rprx-vision`，服务端原端口 443。此前调整 DNS 与微信直连规则后，Wi-Fi、5G 出口检测及微信图片正常。随后断线测试将手机节点端口临时改为 1；反馈称已改回 443、保存并重新开关 VPN，但 5G 下 Safari 的 IPv4 检测页仍打不开，路由显示「配置」。此前 IPv6 专用检测页也失败；当时只读检查显示 VPS 没有公网 IPv6 地址和 IPv6 默认路由、IPv4 请求正常。尚未登录 Claude 或付款。

**完整对话补充：**本客户先通过「配置」模式复用现有微信直连规则，确认微信发图恢复；随后调整 DNS，Wi-Fi、5G 检测及微信发图均取得正常反馈。之后修改手机节点端口做断线测试，出现恢复连接失败。最终客户确认「网页和微信图片都可以」；恢复后的实际参数与最新出口尚需回读。已有恢复反馈时直接核对当前状态、续接流程。

故障发生时，首页只能确认选中节点、VPN 开关和路由模式，未读到节点编辑页保存后的端口，也未取得当次失败日志。现有记录未确定恢复失败的具体原因；依据当前参数和请求结果选择下一步。

**先给客户两个动作：**

> 先打开小火箭首页当前选中的那条节点，进入编辑页，确认端口已经恢复为原来的 **443**。保存并退出，再重新进入同一条节点看一次，确认保存后的值仍是 443。
>
> 接着记下现在的「配置」模式和已使用的配置文件，保留 DNS、微信规则及其他参数。临时将全局路由切到 **「代理」**，选中刚才核对的节点，关闭再开启 VPN；保持当前 5G，打开 [IPv4 检测页](https://api.ipify.org/) 发起一次新请求。告诉我是否显示 IP，或当前页面的具体报错。

有可用工具时协助核对实际页面；Windows＋iPhone 继续按截图与用户实际反馈带做。参数、地址及密钥只在用户本机对照。

**接着按结果处理：**

1. **代理模式恢复、配置模式失败：**优先检查配置文件实际选用的策略／节点、测试域名及 DNS 请求的路由和日志。保留原微信直连规则，针对失败请求逐项修正；模式切换只是对照结果，还不能据此锁定某一条规则。修复后再按用户选择复测原模式，不能把「配置」模式直接记成全局代理验收通过。
2. **代理模式也失败：**核对当前选中节点与原导入资料是否一致：地址、端口、UUID、Flow、SNI、REALITY 参数及 TLS 指纹。每次只恢复有差异的项目。查看此次新请求的小火箭连接日志，区分连接超时／拒绝、握手失败、DNS 失败或规则选路异常。然后通过已有授权访问方式检查 VPS 当前服务状态、443 监听、日志及适用的防火墙规则。服务器能对外访问 IPv4，不等于手机能连到服务器的 443。
3. **只有某一个检测页失败：**再用另一个独立 HTTPS 检测页（如 [Ping0](https://ping0.cc/)）对照。若其他请求正常，检查原站点及其解析；若都失败，继续当前连接排查。节点恢复与参数核对完成后，仍符合全局 CONNECT 超时案例时再进入第 2.2.1 节的 TLS 指纹尝试。
4. **恢复后再继续：**确认手机实际 HTTPS 请求成功、出口对应目标线路，再补齐本章三站、DNS／IPv6、排除路由与断线行为记录。故障未恢复时 `https_ok=false`，其余字段按实际结果记录，保持在手机网络验收阶段。若原验收已完成而后续测试使连接失效，使用 `workflow.py change --scope phone --reason "断线测试后连接未恢复"` 重新检查受影响的手机步骤，沿用原订单历史。

**IPv4 与 IPv6 分开判断：**[ipify 官方说明](https://www.ipify.org/)中，`api.ipify.org` 用于 IPv4，`api6.ipify.org` 只用于 IPv6。VPS 没有可用 IPv6 出口时，经这条线路访问 IPv6 专用地址失败与缺少 IPv6 出口相符；Safari 的泛化报错本身不能确定原因。IPv4 地址也打不开时另查连接恢复。IPv6 页打不开只记录这次请求结果，仍需检查手机原生 IPv6 是否可能绕行，不能单凭失败就标记“无泄露”。

**先解释断线测试的用途：**「接下来检查节点连不上时，检测请求会怎样。这一步会短暂中断测试连接，结束后切回原节点并确认恢复。」443 是本案例的服务端口；改成 1 是此次带做选用的故障模拟方法，不是修复微信的方法，也不是其他客户的固定操作。实际断线行为以请求结果为准。

**后续断线测试的恢复步骤：**先按第 2.2.4 节保存恢复记录，确认回到当前可用状态的入口。先保留原节点和当前选中项，记录可回读的原值。客户端支持时，使用单独的测试副本制造节点不可达，保持原节点不变；仅有原节点可编辑时，先验证原始导入资料或完整备份可读取、恢复入口可用，再单项修改；准备未完成时保留断线检查待办，先完成准备。测试后切回原节点或恢复原值，保存后重新打开核对，恢复本次应使用的路由模式，再验证新的 HTTPS 请求、实际出口及 Codex 联网。把“故障时的行为”和“恢复后验证结果”分开记录，恢复成功后才提交 `disconnect_checked=true`。当前已失联时先恢复，不继续制造新故障。

#### 2.2.3 节点可用，只有微信图片打不开

**本案例处理方案：先恢复可用网络，再使用「配置」模式，让微信走直连、Claude 相关流量走原目标节点。**作者向遇到类似问题的人核实了这一分流方案；本客户也确认现有微信直连规则下发图成功。后续断线测试曾导致恢复失败，完整对话末尾确认网页与微信图片恢复。

对客户先说明：

> 我们先恢复到之前能正常上网的设置，再单独处理微信图片。小火箭使用「配置」模式，让微信走直连，Claude 相关访问继续走原来的节点。配置好以后，两边都测一下。

1. **先恢复正常上网。**已经越调越坏时，按本机备份、已记录的原值和最近改动，回到最后一次确认能正常上网的节点与配置；改过端口或做过断线测试时接第 2.2.2 节。先确认新的 HTTPS 请求成功及目标出口正确，再处理微信分流。当前网络本来就正常时，保留这一状态直接继续。找不到原配置时，先读取已有记录并逐项核对，不猜原值、不在失效配置上叠加修改。
2. **保存可回到的状态。**按第 2.2.4 节保存当前节点、配置文件、实际路由选项与 DNS 的恢复记录。保持服务端、端口、UUID、Flow、SNI、REALITY 参数和 TLS 指纹原样。微信单项异常不触发节点重建、服务端调整或断线测试。
3. **使用「配置」模式，落实微信直连。**读取当前实际加载的配置文件；已有可用配置就沿用，缺少配置时先按当前客户端支持的格式准备最小必要配置。让微信相关请求匹配直连（`DIRECT`）规则，Claude 相关请求继续匹配原目标节点。核对现有微信规则／规则集、实际请求和匹配优先级；已有正确规则直接复用，需要补充时只改相关规则，保留其他设置。配置必须保存并实际加载。切到「配置」只是启用规则分流，完成标准是请求确实匹配到对应策略。
4. **以请求结果确认分流。**重试微信图片发送和加载，查看对应请求是否命中直连；同时检查原 HTTPS 检测与目标出口、Claude 相关请求的节点策略及适用的 DNS／IPv6 检查。按实际请求和已有可信规则识别范围，不凭一个图片域名判断全部微信请求已覆盖，不把整个配置的默认出口改成直连来解决微信问题。当前已是「配置」时直接核对规则与实际命中，不反复切模式。DNS 只有出现具体解析异常时再单独处理，不批量更换。
5. **一次一项，同时验证两边。**微信图片发送／加载恢复、原网络正常、Claude 相关流量仍走目标线路后保留调整；无改善恢复本次改动，原网络变差立即回到最后可用状态。已登录 Claude 的用户可复用当前可用结果；尚未登录的客户按网络与请求路径检查，不提前登录 Claude 来测试微信问题。之后按原手机网络验收继续，不能以微信恢复代替整项验收。

这里是针对微信单应用异常的配置分流方案；本教程常规交付的默认模式保持原有说明。采用本方案时记录实际配置、微信直连命中、Claude 目标节点命中及前后结果，按第 2.2 节对其他路由模式的要求完成验收。

#### 2.2.4 Windows＋iPhone：保存配置与按目标恢复

先记录当前可用状态：手机网络类型、选中节点、路由模式、选中的配置文件名，以及网页和微信各自是否可用。常见配置文件名是 `default.conf`，实际以列表的选中项为准。

**节点和配置文件分别保存：**

1. **Windows 电脑：**Codex 查找本次部署生成的原始节点二维码／导入文件，确认文件可读取、对应当前节点；告诉客户在断网时从哪里重新打开。原始文件用于恢复节点的服务器地址、端口等参数。配置文件另行保存，其中包含 DNS 与分流规则。
2. **iPhone：**先保存小火箭首页与本次要修改的设置页截图到手机相册，记录字段原值；含凭据的原图留在本机。配置列表中，点击当前文件名，查看实际菜单。有导出／分享／副本入口时按页面操作，保存到「文件」App 的「在我的 iPhone／iPad」位置，使用带日期的备份文件名，确认能找到并打开文件后记录完整备份位置。
3. **当前菜单只有「编辑纯文本」时：**打开后全选、复制，粘贴到手机已有的本地文本编辑器或「在我的 iPhone」笔记，保存为带日期的副本，重新打开确认内容已保存、开头和结尾齐全；没有本地保存入口时按下一项记录字段原值。仅复制到剪贴板记为「待保存」。若包含引用的外部规则、策略或模块，另核对依赖；正文副本按实际覆盖范围记录。
4. **全文保存暂未完成时：**先用本机截图／原值记录支持当前字段的单项修改与原值恢复。整份配置替换或主动断线测试等需要完整恢复资料的操作，等相应资料和入口准备好再做。

客户看到「＋」后出现网址输入框，说明这是下载入口，点取消返回配置列表。依据实际菜单继续保存；Windows＋iPhone 的默认备份路径使用手机本地保存。已有明确需要跨机传文件时才使用 Wi-Fi 上传；检查一次页面地址、前台状态和局域网连通性，仍超时就切回手机本地保存，继续当前任务。

**恢复时只选一个已确认目标：**例如「恢复到网页和微信都能用的那次设置」。Codex 列出该目标的节点、路由、配置文件及 DNS 原值，逐项回读当前值，只修正差异。截图、字段记录、全文副本、原始节点文件各注明恢复范围。先前问题的延迟回复与最新明确目标冲突时，询问客户当前已执行到哪一步，再确定下一步，保持恢复指令一致。

给客户的单轮话术示例：

> 现在只操作 iPhone。打开小火箭「首页」，点当前选中那一行右侧的 ⓘ，查看「端口」。这次记录的原值是 443；如果不同，改回 443 并点「保存」。然后退出、重新打开同一行，告诉我现在显示的端口。

回读一致后，下一轮再选中该节点并重新连接，保持同一种网络，用 Safari 打开 [IPv4 出口检测](https://api.ipify.org/)。对照目标出口，再重试微信图片发送／加载。记录「网页恢复」「微信恢复」「出口已核对」的各自结果；仍失败时读本次连接日志和对应错误，继续第 2.2.2 节排查。

#### 2.2.5 DNS 添加：输入、加入列表、保存、回读

有实际 DNS 异常时再进入本节。先读取当前选中的配置文件和「DNS 覆写、直连 DNS、备用 DNS」原值，确认拟修改字段及请求路径。本案例在使用配置分流时采用主 DNS `https://dns.google/dns-query#proxy` 后取得正常检测；按当前客户端和现场问题选择方案，已有正常结果直接复用。

以下针对本案例中带绿色「＋」、红色「－」的列表编辑界面，分三轮带做；页面不同先看当前截图定位。

**第一轮：找到字段。**

> 现在只操作 iPhone。打开小火箭，点底部「配置」，找到当前选中的文件，点右侧 ⓘ，再点「通用」。找到「DNS 覆写、直连 DNS、备用 DNS」这三项，先保存一张原值截图到手机。

**第二轮：添加并确认保存。**确认需要应用本案例方案后，再给出：

> 在第一组「DNS 覆写」输入框粘贴：
> `https://dns.google/dns-query#proxy`
>
> 点这一行左侧绿色「＋」。看到网址成为独立的一行、左边变为红色「－」，才表示加入列表。若该网址已经完整列出，就沿用这一行。
>
> 本轮将主 DNS 替换为这条网址：确认新条目已加入后，删除同组原来的 `system`；「直连 DNS」「备用 DNS」保持刚记录的原值。点右上角「✓」保存，然后退出、重新进入「通用」，确认网址仍完整列在「DNS 覆写」中。

输入框内有文字、键盘收起、客户说「填好了」分别记录为操作进度；以重新打开后能看到完整条目作为保存成功的依据。原值不是本例的 `system` 时，先说明实际要替换的条目；其他配置字段保持原值。

**第三轮：重新连接并复测。**

> 回小火箭「首页」，把连接开关关闭再开启，保持当前 Wi-Fi 或流量不变。用 Safari 刷新 [DNS 检测页](https://ip.net.coffee/claude/)，把 DNS 检测结果反馈给我，再试一次微信图片。

同时核对新的 HTTPS 请求和实际出口。失败时依据本轮记录恢复改动字段并回读；保留仍可用的节点与其他规则。网页检测正常后，DNS 回退与 IPv6 等尚缺项目按实际状态继续记录；解析器的城市标签与实际查询路径分开判断。

### 2.3 电脑和手机时区、定位设置

**手机节点连接后，下一步执行本节，再完成第 3.1 节网络验收，随后进入手机登录与订阅。**AI 主动展示当前设备的具体设置路径，能操作就直接完成；需要用户操作时，每轮给两三个相连动作，按页面结果或用户明确反馈记录完成。已完成且设置未变化的项目直接复用。

**程序和作者都推荐：时区跟节点所在地区一致。**例如洛杉矶节点选 Los Angeles／洛杉矶；希望保留东八区作息时，可统一选择 Taipei／台北（`Asia/Taipei`，UTC+8）。两种方案都要完成电脑和手机的时区设置，AdsPower 同步采用所选时区；定位权限按下方对应设备的步骤设置。

在这一步直接问一次：**“时区推荐跟节点一致；如果您想保留东八区作息，也可以选台北。电脑和手机统一选哪一种？”**提供“跟随节点（推荐）／台北”两个选项。已有明确选择就复用。节点城市由 AI 读取已有记录与出口结果确定；Apple 商店继续使用美区账户。

用户选好后，直接把下面对应的电脑与手机具体操作步骤展示在聊天中，按所选城市填好；工具能代做时连续完成。Mac 关闭自动时区与系统服务“设定时区”，定位总开关保持原有状态；其他设备按各自步骤设置，手动时区采用所选城市。

#### Windows 上怎么改

按 [Windows 专章第 7 节](10-windows.md)在「设置 → 时间和语言 → 日期和时间」关闭自动设置时区、手动选择已选方案的时区（节点城市或台北）并核对夏令时，保留自动校时。Windows 11 打开「设置 → 隐私和安全性 → 位置」，Windows 10 打开「设置 → 隐私 → 位置」，关闭设备定位服务并复查。手机为 iPhone／iPad 时执行下方步骤；安卓执行[安卓时区与定位步骤](11-android-web-pay.md#手机代理配置后时区与定位)。

#### Mac 上怎么改

1. 打开 **系统设置 → 通用 → 日期与时间**，关闭「自动设置时区」（部分版本显示「使用当前位置自动设置时区」），保留自动设置日期与时间。
2. 在时区的「设置……」中搜索并选择已选城市（节点城市或台北）。
3. 打开 **系统设置 → 隐私与安全性 → 定位服务 → 系统服务 → 详细信息**，关闭「设定时区」（名称按当前系统界面），完成后返回。
4. Mac 的「定位服务」总开关保持原有状态。在已配置的 AdsPower 环境中，将地理位置设为「禁止」，核对 Claude 网页的位置权限为禁止。
5. 返回 **通用 → 日期与时间**，复查时区城市，记录自动时区、系统服务「设定时区」、城市复查结果及 Claude 网页位置权限。

#### iPhone／iPad 上怎么改

1. 打开 **设置 → 通用 → 日期与时间**，关闭「自动设置」。
2. 点「时区」，搜索并选择已选城市（节点城市或台北）。
3. 打开 **设置 → 隐私与安全性 → 定位服务 → 系统服务**，关闭「设定时区」。
4. 返回 **设置 → 隐私与安全性 → 定位服务**，关闭顶部「定位服务」总开关，按系统提示完成关闭。
5. 返回 **设置 → 通用 → 日期与时间**，复查时区城市，记录自动设置、系统服务「设定时区」、定位总开关及城市复查结果。

若定位总开关原本已关闭，保持关闭，系统服务「设定时区」记录为“随总开关停用”；恢复定位后重新检查该子开关。定位关闭期间，地图等依赖定位的功能会受到影响；记录原值，用户结束本次使用后需要恢复时按原值恢复，并将对应检查项更新为待完成。

#### 设置完成后接哪一步

把电脑系统、手机系统和 AdsPower 的实际时区并排核对，统一采用已选时区方案；节点方案跟随实际出口，台北方案统一使用 `Asia/Taipei`；AdsPower 地理位置为「禁止」。记录城市／时区标识与当前偏移，规则等效的城市可以采用。VPS 服务器的 UTC 系统时间保持原配置。

**完成记录分开保存：电脑网络、手机网络、电脑时区、电脑定位、手机时区、手机定位、AdsPower 时区与地理位置。**网络连通只完成网络项。AI 在当前步骤展示设置路径并完成上述项目后，运行[登录前衔接检查](06-before-login.md#登录前衔接脚本)；缺哪项就继续哪项，齐全后直接进入 Apple 准备、手机 Google 登录和 Pro 订阅。已有登录、账户和余额直接复用。

## 3. 手机网络与交付检查

### 3.1 手机端完成标准

先逐项记录：镜像与 Computer Use 是否可用（不可用时写排查结果和替代方式）、客户端与目标节点、节点参数核对结果、全局路由模式、客户端连接状态及系统 VPN 状态。小火箭默认核对「代理」；其他模式按第 2.2 节的明确选择与实际路径验收处理。模式未见到或实际路径未验证时先补检，不把未知结果记通过。

手机客户端显示连接后，先在**手机自己的浏览器**打开 [Claude IP 检测](https://ip.net.coffee/claude/)、[Ping0](https://ping0.cc/) 和 [Scamalytics](https://scamalytics.com/ip)，记录设备、时间、网络类型、实际出口地区和各站结果，核对公网出口、IPv4 / IPv6 和 DNS，检查客户端是否存在绕过代理的排除路由。三站量表分别记录，每站都要有实际数值和结果说明；未出分或打不开先留在当前步骤补检，电脑分数不代填手机结果。第三方评分不能代替实际路由检查。

官方 Claude App 安装后，先在未登录状态下结合客户端连接日志核对可观察到的 Claude 相关请求、命中规则和节点；首次登录后的实际请求再复核。手机浏览器的结果不能单独证明 App 使用了同一条线路；日志未能覆盖的路径记「未验证」，不能宣称全部 App 流量已确认。

如果平时会从 Wi-Fi 切到蜂窝网络，两种网络都要检查；当前不使用的网络记「不适用（切换前补检）」，不能用 Wi-Fi 结果代替蜂窝结果。需要验证断线行为时，确认没有登录、付款或其他不能中断的工作，用未登录的测试页面分别测试节点不可达（VPN 保持开启）与主动关闭 VPN，并按第 2.2.2 节回读恢复后的节点参数、恢复连接和本次应使用的路由模式，再验证新的 HTTPS 请求与实际出口。节点故障后发生自动直连时先修复；不能确认时记「未验证」。主动关闭 VPN 后可能恢复手机原网络，不能宣称普通小火箭设置提供系统级永久断网保护；必须提醒用户先停止 Claude 使用，恢复 VPN 并复查后才继续。

**手机网络、时区和定位分别完成后，接手机登录与订阅。**适用项未通过或未验证时，先带用户修复或补检；客户暂缓时保存当前待办，恢复后接着完成。模式、节点、Wi-Fi／蜂窝网络、DNS／排除路由变化，或 VPN 重连后结果有疑问时，重新检查受影响项目。电脑端已通过，不等于手机端已通过。

### 3.2 交付前统一核对

- 电脑：AdsPower 环境名称、本机入口、出口、DNS / WebRTC、语言时区及断线测试有记录。
- 手机：镜像操作或排查与替代方式有记录；节点已导入，小火箭采用默认「代理」或已核对目标请求路径的「配置」模式、VPN 已连接；实际使用的 Wi-Fi / 蜂窝网络、出口、IPv6 / DNS、排除路由、Claude App 路径、断线行为、时区设置与复查、定位总开关分别有结果。
- 每项只填写「通过 / 未通过 / 未验证」。能打开网页、第三方分数较高，都不能替代上述检查，也不能作为不封号或免身份验证的承诺。

交给 Codex 的检查提示词：

请按本文完成标准分别核对 AdsPower 浏览器和手机。先读取配置，再检查各端实际请求路径；不要因为浏览器检查通过就把其他端也标为通过。输出检查项目、结果、证据和未完成原因，隐藏所有密钥和个人信息。不要改动我已有的浏览器环境，不进行注册、付款或提交身份材料。需要断线测试时先确认是否会中断 Codex 或其他当前工作；会中断 Codex 时按网络章节提前交代手动恢复方法并确认用户会恢复，没有恢复办法则记未验证。完成后恢复连接并确认 Codex 可以继续。
